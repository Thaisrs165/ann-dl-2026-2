    Exercises → VAE

    Implementation approach. All the VAE code lives in one module, code/vae.py: the data loading and split, the VAE class, the reparameterization, the loss, and the training loop. Both exercise scripts import it unchanged; Exercise 2 only passes d=2 instead of d=16. torch.nn is used for the linear layers, ReLU and sigmoid, and autograd computes the gradients, which this activity allows. The VAE-specific parts are written by hand: the reparameterization \(\mathbf z=\boldsymbol\mu+\boldsymbol\sigma\odot\boldsymbol\varepsilon\), the summed BCE, the closed-form KL, and the sampling from the prior. No VAE class and no torch.distributions are used.

    Randomness. The split uses torch.Generator().manual_seed(42), as given. train_vae calls torch.manual_seed(42) immediately before building each model. That one call fixes the initial weights, the shuffle of every epoch and every \(\boldsymbol\varepsilon\) drawn during training. Figure 3 draws its prior samples after torch.manual_seed(0). Exercise 2 needs Exercise 1's \(d=16\) model for Figure 6, so it rebuilds it with the same seed and the same sequence of calls. That run reproduces Exercise 1's test numbers exactly (82.07 / 19.41 nats), which confirms it is the same model. Everything runs on CPU, about 25 s per model (torch 2.15). To reproduce, run from the repository root (MNIST is downloaded to ./data on the first run):

    python docs/exercises/vae/code/exercise1_vae.py
python docs/exercises/vae/code/exercise2_latent2d.py

    Units. Every loss number on this page is in nats per image: summed over the 784 pixels (reconstruction) or over the \(d\) latent dimensions (KL), then averaged over the images.

    def load_mnist(root: str = "data"):
    """Return (x_train, x_val, x_test, y_test) as flattened float tensors in [0, 1].

    The split is exactly the one in the statement: 50 000 / 10 000 out of the
    60 000 training images, with ``torch.Generator().manual_seed(42)``. The
    10 000 official test images are kept apart and only used for the final
    numbers (and the figures drawn after training).
    """
    train_full = datasets.MNIST(root, train=True, download=True, transform=transforms.ToTensor())
    test = datasets.MNIST(root, train=False, download=True, transform=transforms.ToTensor())
    train, val = random_split(train_full, [50_000, 10_000],
                              generator=torch.Generator().manual_seed(42))

    # ToTensor() already maps pixels to [0, 1]; dividing the raw uint8 array by
    # 255 gives the same values and avoids 70 000 PIL round-trips. The subsets'
    # .indices are the ones random_split drew above.
    all_x = train_full.data.float().div(255).view(-1, 784)
    x_train = all_x[torch.tensor(train.indices)]
    x_val = all_x[torch.tensor(val.indices)]
    x_test = test.data.float().div(255).view(-1, 784)
    return x_train, x_val, x_test, test.targets.clone()

    The split is the one in the statement: 50 000 training and 10 000 validation images drawn from the 60 000 MNIST training images, plus the 10 000 official test images. To avoid 70 000 PIL conversions, the pixels are read straight from the dataset's uint8 array and divided by 255. That is exactly what ToTensor() computes, and the rows are selected with the indices that random_split returned. Images are flattened to 784-vectors with values in \([0,1]\).

    Use of the test set. train_vae only receives x_train and x_val, so every quantity logged during training (Figure 1) comes from those two sets. The test set is touched only after training has finished: for the final numbers of each model, and for the figures drawn from the trained model (2, 4, 5 and 6).

    class VAE(nn.Module):
    """Encoder 784 -> 512 -> 256 (ReLU), heads 256 -> d for mu and log sigma^2,
    decoder d -> 256 -> 512 -> 784 (ReLU on the hidden layers, sigmoid output)."""

    def __init__(self, d: int):
        super().__init__()
        self.encoder = nn.Sequential(
            nn.Linear(784, 512), nn.ReLU(),
            nn.Linear(512, 256), nn.ReLU(),
        )
        self.fc_mu = nn.Linear(256, d)       # head for mu
        self.fc_logvar = nn.Linear(256, d)   # head for log sigma^2 (unconstrained, so sigma > 0 always)
        self.decoder = nn.Sequential(
            nn.Linear(d, 256), nn.ReLU(),
            nn.Linear(256, 512), nn.ReLU(),
            nn.Linear(512, 784), nn.Sigmoid(),   # each output = P(pixel is "on")
        )

    def encode(self, x):
        h = self.encoder(x)
        return self.fc_mu(h), self.fc_logvar(h)

    def decode(self, z):
        return self.decoder(z)

    def forward(self, x):
        mu, logvar = self.encode(x)
        z = reparameterize(mu, logvar)
        return self.decode(z), mu, logvar


def reparameterize(mu, logvar):
    """z = mu + sigma * eps with eps ~ N(0, I).

    The randomness lives in eps, which does not depend on the parameters, so
    gradients flow through mu and sigma = exp(logvar / 2) as usual.
    """
    sigma = torch.exp(0.5 * logvar)
    eps = torch.randn_like(sigma)
    return mu + sigma * eps


def vae_loss(x_hat, x, mu, logvar, beta: float = 1.0):
    """Return (total, recon, kl), each averaged over the images of the batch.

    recon = -sum_j [x_j log x_hat_j + (1 - x_j) log(1 - x_hat_j)]   (784 pixels)
    kl    = 1/2 sum_i (mu_i^2 + sigma_i^2 - 1 - log sigma_i^2)      (d latent dims)

    reduction="sum" then / batch size keeps the BCE summed over pixels;
    reduction="mean" would also divide it by 784 and silently weaken it
    relative to the KL.
    """
    n = x.shape[0]
    recon = F.binary_cross_entropy(x_hat, x, reduction="sum") / n
    kl = 0.5 * torch.sum(mu.pow(2) + logvar.exp() - 1.0 - logvar) / n
    return recon + beta * kl, recon, kl
    Part Layers
    Encoder \(784 \to 512 \to 256\), ReLU after each
    Heads fc_mu: \(256 \to d\) for \(\boldsymbol\mu\); fc_logvar: \(256 \to d\) for \(\log\boldsymbol\sigma^2\)
    Decoder \(d \to 256 \to 512 \to 784\), ReLU after the hidden layers, sigmoid at the output
    Latent size \(d=16\) (Exercise 1), \(d=2\) (Exercise 2)

    The loss for one image, implemented in vae_loss and averaged over the batch:

    \[ L=\underbrace{-\sum_{j=1}^{784}\Big[x_j\log\hat x_j+(1-x_j)\log(1-\hat x_j)\Big]}_{\text{reconstruction}} \;+\;\beta\cdot\underbrace{\tfrac12\sum_{i=1}^{d}\left(\mu_i^2+\sigma_i^2-1-\log\sigma_i^2\right)}_{\mathrm{KL}\left(q(\mathbf z\mid\mathbf x)\,\|\,\mathcal N(\mathbf 0,\mathbf I)\right)}, \qquad \beta=1 . \]
    • Reconstruction: F.binary_cross_entropy(x_hat, x, reduction="sum") / n sums over all pixels of the batch and divides by the number of images. That gives the per-image sum over the 784 pixels, the Bernoulli negative log-likelihood \(-\log p(\mathbf x\mid\mathbf z)\).
    • KL: the closed form above, written out as 0.5 * sum(mu² + exp(logvar) − 1 − logvar) / n. The encoder outputs \(\log\sigma^2\) rather than \(\sigma\), so \(\sigma^2=e^{\log\sigma^2}\) is always positive without any constraint.
    • Reparameterization: reparameterize draws \(\boldsymbol\varepsilon\sim\mathcal N(\mathbf 0,\mathbf I)\) with randn_like and returns \(\boldsymbol\mu+e^{\frac12\log\boldsymbol\sigma^2} \odot\boldsymbol\varepsilon\). The noise does not depend on the parameters, so the gradient of the reconstruction term reaches the encoder through \(\boldsymbol\mu\) and \(\boldsymbol\sigma\).
    • evaluate uses the same forward pass, with a sampled \(\mathbf z\), so the validation and test numbers are the same single-sample estimate of the negative ELBO that training minimises.

    @torch.no_grad()
def evaluate(model, x, batch_size: int = 1000):
    """Average recon and KL (nats/image) over a whole set, with z sampled as in training."""
    model.eval()
    recon_sum = kl_sum = 0.0
    for i in range(0, len(x), batch_size):
        xb = x[i:i + batch_size]
        x_hat, mu, logvar = model(xb)
        _, recon, kl = vae_loss(x_hat, xb, mu, logvar)
        recon_sum += recon.item() * len(xb)   # undo the per-batch average
        kl_sum += kl.item() * len(xb)
    return recon_sum / len(x), kl_sum / len(x)


def train_vae(d: int, x_train, x_val, epochs: int = EPOCHS, verbose: bool = True):
    """Build a VAE with latent size d (after torch.manual_seed(42)) and train it.

    Returns the model and a history dict with, per epoch, the training recon/KL
    (average over the epoch's mini-batches) and the validation recon/KL
    (evaluated at the end of the epoch). Only the validation set is looked at
    during training; the test set never enters this function.
    """
    torch.manual_seed(42)   # fixes the initial weights, the shuffles and every eps
    model = VAE(d)
    opt = torch.optim.Adam(model.parameters(), lr=LR)
    hist = {k: [] for k in ("train_recon", "train_kl", "val_recon", "val_kl")}

    t0 = time.time()
    for epoch in range(1, epochs + 1):
        model.train()
        perm = torch.randperm(len(x_train))   # new shuffle every epoch
        recon_sum = kl_sum = 0.0
        for i in range(0, len(x_train), BATCH_SIZE):
            xb = x_train[perm[i:i + BATCH_SIZE]]
            x_hat, mu, logvar = model(xb)
            loss, recon, kl = vae_loss(x_hat, xb, mu, logvar)
            opt.zero_grad()
            loss.backward()
            opt.step()
            recon_sum += recon.item() * len(xb)
            kl_sum += kl.item() * len(xb)

        hist["train_recon"].append(recon_sum / len(x_train))
        hist["train_kl"].append(kl_sum / len(x_train))
        v_recon, v_kl = evaluate(model, x_val)
        hist["val_recon"].append(v_recon)
        hist["val_kl"].append(v_kl)
        if verbose:
            print(f"[d={d:2d}] epoch {epoch:2d}  train recon {hist['train_recon'][-1]:7.2f}  "
                  f"KL {hist['train_kl'][-1]:6.2f}  |  val recon {v_recon:7.2f}  KL {v_kl:6.2f}"
                  f"  ({time.time() - t0:5.1f}s)")
    return model, hist

    E — Analysis

    Why the KL rises while the total loss falls (Figure 1). At initialisation the encoder's heads output \(\boldsymbol\mu\approx\mathbf 0\) and \(\log\boldsymbol\sigma^2\approx\mathbf 0\), so \(q(\mathbf z\mid\mathbf x)\approx\mathcal N(\mathbf 0,\mathbf I)\) for every image. That makes the KL almost zero. It also means \(\mathbf z\) carries no information about \(\mathbf x\): the decoder can only output something like the average digit, and the reconstruction term is very large. The KL is the price of information. Moving \(\boldsymbol\mu\) away from 0 and shrinking \(\boldsymbol\sigma\) is what lets \(\mathbf z\) say which image it came from, and the KL charges for exactly that. The optimizer pays as long as one extra nat of KL buys more than one nat of reconstruction, and early in training it buys far more. On the validation set, from epoch 1 to epoch 20 the KL rises by 6.78 nats (12.60 → 19.38) while the reconstruction falls by 46.81 nats (129.50 → 82.69), so the total drops by 40.0 nats. After about epoch 10 the KL flattens near 19.4. From there, more information in \(\mathbf z\) costs about as much KL as it saves in reconstruction. The same balance shows up per dimension. On the test set, 5 of the 16 latent dimensions have KL 0.00 (posterior \(\sigma\approx 1\), \(\mu\approx 0\), i.e. the prior itself). The optimizer decided that using them would cost more KL than it saves. The 11 active dimensions each cost between 1.08 and 2.51 nats.

    Why Figure 3 looks worse than Figure 2: two separate reasons.

    1. Where the prior samples land. The KL pulls each \(q(\mathbf z\mid\mathbf x)\) toward \(\mathcal N(\mathbf 0,\mathbf I)\) but does not make them equal to it. On the active dimensions the posteriors are narrow (mean \(\sigma=0.197\), against 1 for the prior), so each training image only covers a small ball of latent space. The union of those balls (the aggregate posterior) has gaps and low-density regions that the prior still assigns mass to. During training, the decoder only ever sees codes drawn from these balls. A prior sample often lands in a gap. Measured on the test set, the 64 prior samples of Figure 3 are a median 2.61 away from the nearest encoded test image (\(\boldsymbol\mu\)). A test code's nearest other test code is a median 1.26 away. So the prior samples sit about twice as far from the data as the data sits from itself, in places where the decoder was never trained. There it produces faint strokes or shapes between classes, like the scribbles in rows 2 and 7.
    2. What the decoder outputs for a given \(\mathbf z\). The decoder does not output an image. It outputs, for each pixel, the probability \(\hat x_j\) that it is on. The value that minimises the BCE is the average of \(x_j\) over all the training images that could have produced that \(\mathbf z\). Whenever several images (different slants, thicknesses, or even different digits) are compatible with the same \(\mathbf z\), the output is their pixel-wise average. A stroke that sits in slightly different places in those images becomes a wide grey band, and the result is blur. Figure 2 decodes \(\boldsymbol\mu\) of one real image, the most specific point of that image's posterior, so the average is over a narrow set of images that all look alike. A random prior sample is, more often, a point many different images could have produced, so its average is blurrier. (We plot \(\hat x_j\) itself rather than Bernoulli-sampled pixels, so the uncertainty shows up as grey.)

    Why decode \(\boldsymbol\mu\), not a sampled \(\mathbf z\), in Figure 2. Figure 2 is meant to show what the model encoded about each image. \(\boldsymbol\mu\) is the centre (and the mode) of the posterior \(q(\mathbf z\mid\mathbf x)\). Decoding it gives the model's best single guess, and the result is deterministic and reproducible. A sampled \(\mathbf z=\boldsymbol\mu+\boldsymbol\sigma \odot\boldsymbol\varepsilon\) adds random noise of size \(\sigma\approx 0.2\) on each active dimension. That shows a random neighbour instead (another slant or thickness, sometimes a different digit), so the figure would mix reconstruction quality with sampling noise. Sampling is what the ELBO needs during training. For displaying a reconstruction, it only adds noise.

    The grid points are \(z=\Phi^{-1}(q)\) for 15 evenly spaced \(q\in[0.05,0.95]\), giving \(z\in\{-1.645,-1.204,\ldots,0,\ldots,1.204,1.645\}\) on each axis. The rows run from \(z_2=1.645\) at the top to \(-1.645\) at the bottom, so Figure 5 has the same orientation as Figure 4.

    Why this spacing. Neighbouring grid values are always \(\Delta q = 0.9/14 \approx 0.064\) apart in cumulative probability, and the prior factorises as \(\mathcal N(0,1)\times\mathcal N(0,1)\). So every cell between neighbouring grid points holds the same prior mass, \((0.064)^2\approx 0.0041\). The grid is dense near the origin, where the prior (and the data) are concentrated, and sparse in the tails. A linear grid would spend most of its cells on regions the prior almost never samples.

    E — Analysis

    Which digits overlap (Figure 4), and the same transition in Figure 5. The largest overlap is 4 and 9. Their clusters sit on top of each other just above the centre: the medians are about 0.15 apart, and the pink and brown points are interleaved. Next comes the 3/5/8 group below the centre, with a weaker 7–9 contact. To put numbers on it, each test \(\boldsymbol\mu\) was classified by majority vote of its 10 nearest other test \(\boldsymbol\mu\)s. The pairs most often mixed up, counting both directions, are 4–9 (621 images), 3–5 (360), 3–8 (162), 5–8 (160) and 7–9 (158). Overall 10-NN accuracy is 0.789. Per digit it is lowest for 9 (0.56), 5 (0.57) and 4 (0.66), and highest for 1 (0.98) and 0 (0.97). In Figure 5 the 4→9 transition runs along the rows \(z_2\approx0.50\)–\(0.92\), moving right from \(z_1\approx-0.5\) to \(0.5\). On the row \(z_2=0.70\) the cells read 6, 6, 6, a blurry 6/4, then a sequence of 4s whose top gradually closes, then 9s from \(z_1\approx0.50\). The in-between images are plausible hybrids rather than blends: a 4 with its two upper strokes pulled together until they form the 9's closed loop. Some cells look like either digit. Where three classes meet (\(z_2\approx0.16\)–\(0.33\), \(z_1\approx-0.33\)–\(0\), between 2, 4 and 6) the cells do become grey overlapping strokes that are no digit. The 3/5/8 region below the centre does the same: 8 → 3 down the column \(z_1\approx-0.16\), and along the bottom rows 5s on the left, 3s in the middle and 5s again on the right, with in-between 3s whose upper-left stroke opens into the 5's flag.

    What two numbers per image force the model to throw away. Reconstruction goes from 82.07 to 135.22 nats (+53.15 per image). Two coordinates are mostly spent on which digit it is. The plane is carved into ten class regions, so within each class only about one continuous degree of freedom is left, and every individual detail must be discarded. Figure 5 shows this. Each digit appears as one smooth, averaged prototype that varies along a single direction. The 1s in the right-hand columns only change slant, from vertical at the top to leaning right at the bottom. The 0s on the left only change width and tilt. The 7s at the top right only change the angle of their stem. Nothing in the plane encodes stroke thickness independently of identity, or the small hooks, serifs, gaps and loops that make one person's 7 different from another's. Every reconstruction is pulled to the nearest prototype, and the BCE charges for every pixel where the real stroke differs. The per-digit test reconstruction (from \(\boldsymbol\mu\)) supports this. The loss is smallest for the simplest shape, 1 (50.8 nats for \(d=2\) vs 35.5 for \(d=16\)), and largest for the shapes with the most variation, 2 (169.1 vs 92.4) and 8 (161.9 vs 97.2). The KL is lower too (6.70 vs 19.41), and that is no saving: it simply means \(\mathbf z\) carries less information about each image.

    The two rows of Figure 6. The latent row passes through images that look like digits. The 1 grows a foot at \(t=0.33\), becomes a clear 2 at \(t=0.44\)–\(0.67\), and the 2's lower stroke then curls into the 3, so every frame is one coherent stroke. The pixel row does not. Every in-between frame is the 1 and the 3 superimposed at partial intensity, for example the 3 with a grey slash through it at \(t=0.44\)–\(0.56\). That is not a digit. Images of digits do not form a convex set in pixel space. The strokes of the 1 and the 3 occupy different pixels, so averaging pixels cannot move a stroke from one place to the other. It only dims one image while brightening the other. In latent space, the KL term packs the codes of all training images into one continuous region around the origin. The straight line from \(\boldsymbol\mu_a\) to \(\boldsymbol\mu_b\) therefore runs through codes that real images (here, 2s) also occupy. The nonlinear decoder maps each of those points to a single coherent image, so moving \(\mathbf z\) moves the strokes instead of cross-fading them. This holds only where the line stays inside the region covered by data. The 0 → 1 pair mentioned in 2D shows that a line can cross a gap between clusters, and the frames in that gap smear.
